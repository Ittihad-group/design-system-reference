## SA-01 · المستخدمون — P0 · [Approved] (دورة الحياة [Pending])

**Epic story:** كمدير نظام أريد أنشئ المستخدمين وأربطهم بدور وقسم وأتحكم في دورة حياة حساباتهم، عشان محدش يدخل النظام إلا بصلاحية معروفة ومسجّلة.

### الشاشات
| ID | الاسم | النوع | Route |
|----|-------|-------|-------|
| SCR-USR-01 | قائمة المستخدمين | List | `/super-admin/users` |
| SCR-USR-02 | معالج مستخدم جديد (3 خطوات) | Wizard | `/super-admin/users/new` |
| SCR-USR-03 | درج تفاصيل المستخدم (بيانات · الدور والنطاق · الجلسات والأجهزة · النشاط) | Drawer | `/super-admin/users/:id` |
| SCR-USR-04 | حوارات: تعطيل · فك قفل · إعادة تعيين · خروج إجباري | Dialogs | — |
| SCR-USR-05 | شريط Bulk Actions | Component | — |
| SCR-USR-06 | صفحة تفعيل الحساب (للمستخدم الجديد) | Public page | `/activate/:token` |

**السلوك في القائمة:** أعمدة: مستخدم · دور · قسم · حالة · MFA · آخر دخول · إجراءات. فلاتر: بحث، دور، قسم، حالة، MFA. Pagination. Bulk: تعطيل، نقل قسم، تصدير.

### Use Cases
**UC-USR-01 · إنشاء مستخدم** — الممثل: Super Admin (أو من عنده `sa.users.create`) · المحفز: «مستخدم جديد»
- شروط: عنده الصلاحية · الدور والقسم موجودين.
- المسار: 1) بيانات (اسم، بريد، هاتف، لغة) ← 2) دور وقسم + مدير مباشر + مخازن (لو مدير مخزن) ← 3) مراجعة وإرسال رابط التفعيل.
- استثناءات: بريد مكرر ← خطأ على الحقل · دور Super Admin ← Step-up + يظهر تحذير · قسم معطّل ← مش في الاختيارات.
- النتيجة: مستخدم `pending` + رسالة تفعيل · Audit `USER.CREATED`.

**UC-USR-02 · تغيير دور/قسم مستخدم** — الممثل: Super Admin
- المسار: فتح الدرج ← تبويب "الدور والنطاق" ← اختيار الدور الجديد ← عرض الفرق في الصلاحيات ← تأكيد + سبب ← حفظ.
- استثناءات: المستخدم هو نفسه (ممنوع) · آخر Super Admin (ممنوع) · الدور الجديد Super Admin ← Step-up.
- النتيجة: الجلسات النشطة للمستخدم تتحدّث (UC-GLB-05) · `USER.ROLE_CHANGED` قبل/بعد.

**UC-USR-03 · تعطيل / تفعيل مستخدم**
- المسار: قائمة الصف ← تعطيل ← Confirm مع الأثر («هتنتهي جلساته فورًا») + سبب ← تنفيذ.
- بدائل: تعطيل جماعي (Bulk) ← ملخص بالعدد.
- استثناءات: آخر Super Admin نشط ← ممنوع · عنده طلبات اعتماد معلّقة ← تحذير بتحويلها **[New]**.
- النتيجة: كل جلساته وأجهزته تُلغى · `USER.DISABLED` / `ENABLED`.

**UC-USR-04 · فك قفل حساب موقوف** — من القائمة أو من مركز الأمان (SA-18) ← Confirm + سبب ← الحالة `active` ← `USER.UNLOCKED`.

**UC-USR-05 · إعادة تعيين كلمة المرور** — خياران: (أ) رابط مؤقت للبريد المسجل **[Pending بند 15]** (ب) تعيين من الأدمن (حسب `flows.md`) ← Step-up ← `AUTH.PASSWORD_RESET_REQUESTED`. صلاحية الرابط **{Open}**.

**UC-USR-06 · خروج إجباري** — إنهاء كل جلسات المستخدم ← Confirm ← `USER.FORCE_LOGOUT`.

**UC-USR-07 · تفعيل الحساب بواسطة المستخدم** — الممثل: المستخدم الجديد ← فتح الرابط ← تعيين كلمة مرور (حسب السياسة SA-15) ← إعداد MFA لو مطلوب ← الحالة `active`. رابط منتهي ← «اطلب رابطًا جديدًا من مدير النظام».

**UC-USR-08 · بحث وفلترة وتصدير** — تصدير CSV للنتيجة المفلترة (`sa.users.export`) ← `EXPORT.DATA`.

### User Stories + AC
- **US-USR-01** كمدير نظام أريد إنشاء مستخدم بدور وقسم.
  - AC: لا يُنشأ بدون بريد فريد ودور · يستلم رابط التفعيل · يظهر في القائمة بحالة "بانتظار التفعيل" · سجل التدقيق فيه الحدث.
- **US-USR-02** كمدير نظام أريد تعطيل مستخدم فورًا.
  - AC: يُسجَّل خروجه من كل الأجهزة خلال الجلسة الحالية · لا يقدر يدخل · يظهر "معطّل" · السبب محفوظ.
- **US-USR-03** كمدير نظام لا أريد أن أُقفل نفسي خارج النظام.
  - AC: لا يمكن تعطيل أو تخفيض آخر Super Admin نشط · رسالة تشرح السبب.
- **US-USR-04** كمدير نظام أريد أفلتر المستخدمين بالدور والقسم والحالة.
  - AC: الفلاتر تتجمّع · chips للفلاتر النشطة · "مسح الكل".

### البيانات
`User` (انظر الكتالوج). قيود: البريد فريد وغير قابل للتغيير بعد التفعيل **[New]** (تغييره عملية منفصلة) · `manager_id` لا يشاور على المستخدم نفسه ولا يعمل حلقة.

### قواعد
- **BR-USR-01** مفيش حذف نهائي؛ تعطيل فقط **[New]** (بند 4 في قرارات README).
- **BR-USR-02** المستخدم لا يغيّر دور نفسه **[New]**.
- **BR-USR-03** التاجر ليس مستخدمًا داخليًا ولا يظهر هنا (بند 34 Pending).
- **BR-USR-04** حد القفل بعد المحاولات الفاشلة **{Open}**.

### حالات حدّية
- مستخدم له طلبات اعتماد معلّقة ويُعطَّل · مدير مباشر اتعطّل ← الفريق بدون مدير (تنبيه) · قسم اتغيّر وعليه نطاق "الفريق".

## SA-02 · الأدوار والصلاحيات (RBAC) — P0 · [Approved]

**Epic story:** كمدير نظام أريد أنشئ أدوارًا وأعدّل صلاحياتها لكل موديول، عشان كل موظف يشوف ويعمل اللي يخصه بس.

### الشاشات
| ID | الاسم | النوع | Route |
|----|-------|-------|-------|
| SCR-ROL-01 | الأدوار + مصفوفة الصلاحيات (split) | Master-detail | `/super-admin/roles` |
| SCR-ROL-02 | دور جديد (من الصفر / نسخ) | Wizard | `/super-admin/roles/new` |
| SCR-ROL-03 | أعضاء الدور | Tab | `/super-admin/roles/:id/members` |
| SCR-ROL-04 | مقارنة دورين | Page [New] | `/super-admin/roles/compare` |
| SCR-ROL-05 | معاينة "شوف كأنك دور" | Overlay [New] | — |
| SCR-ROL-06 | ملخص الفروقات قبل الحفظ | Dialog | — |

### Use Cases
**UC-ROL-01 · إنشاء دور** — بداية من الصفر أو نسخ دور موجود ← اسم عربي/English + وصف ← مصفوفة ← حفظ. `ROLE.CREATED`.
- استثناء: اسم مكرر · محاولة إنشاء دور بصلاحية أعلى من صلاحيات الأدمن الحالي (غير ممكن لأن Super Admin كامل).

**UC-ROL-02 · تعديل مصفوفة دور**
- المسار: اختيار الدور ← تغيير الخانات (عرض/إضافة/تعديل/حذف/اعتماد/تصدير) ← شريط "تغييرات غير محفوظة" ← حفظ ← ملخص الفروقات («هتضيف: اعتماد الخصم») ← Step-up ← تنفيذ.
- قاعدة: إلغاء «عرض» يلغي ما بعده تلقائيًا مع تنبيه.
- النتيجة: المستخدمون بالدور يتأثروا فورًا · `ROLE.UPDATED` بالفروقات.

**UC-ROL-03 · حذف دور** — ممنوع لو فيه مستخدمين (ينقلهم الأول UC-ROL-06) · ممنوع لدور محمي · Confirm + سبب · `ROLE.DELETED`.

**UC-ROL-04 · مقارنة دورين [New]** — عرض الفروق جنب بعض (مضاف/مفقود/مختلف النطاق).

**UC-ROL-05 · معاينة كأنك دور [New]** — يعرض القائمة والشاشات اللي الدور هيشوفها **بدون انتحال هوية أي مستخدم**، ولا ينفّذ أي إجراء.

**UC-ROL-06 · نقل أعضاء دور** — اختيار مستخدمين ← دور بديل ← تأكيد ← `USER.ROLE_CHANGED` لكل واحد.

### User Stories + AC
- **US-ROL-01** كمدير نظام أريد مصفوفة موديول × 6 عمليات.
  - AC: الأعمدة: عرض · إضافة · تعديل · حذف · اعتماد · تصدير · «عرض» شرط للباقي · عمود الاعتماد بلون Accent · الخانة المعطّلة بسبب.
- **US-ROL-02** كمدير نظام أريد أشوف الفرق قبل الحفظ.
  - AC: ملخص بالنص لكل تغيير · زر تراجع · لا حفظ بدون تأكيد.
- **US-ROL-03** كمدير نظام لا أريد أحذف دورًا مستخدَمًا.
  - AC: الحذف معطّل مع سبب وعدد المستخدمين.
- **US-ROL-04** كمدير نظام أريد أعرف مين عليه الدور.
  - AC: تبويب الأعضاء بالأسماء والحالات.

### قواعد
- **BR-ROL-01** دور Super Admin مقفول (لا تعديل ولا حذف).
- **BR-ROL-02** موظف المبيعات لا يرى التكاليف الداخلية ولا التقارير المالية ولا أرباح المصنع (**Approved بند 25**) — يتحقق في الخادم.
- **BR-ROL-03** الأدوار المبدئية **[Pending بند 5]**؛ موديول الجودة خارج v1 قبل الاعتماد (**بند 34**).

## SA-03 · نطاق البيانات والصلاحيات الحساسة — P0 · [New — آلية لقواعد Approved]

**Epic story:** كمدير نظام أريد أحدد "إيه اللي يقدر يشوفه الدور من البيانات" و"مين يقدر يعمل العمليات الحساسة"، لأن المصفوفة وحدها مش كفاية.

### الشاشات
| ID | الاسم | النوع |
|----|-------|-------|
| SCR-SCP-01 | محدد النطاق داخل صف المصفوفة (ذاتي · الفريق · القسم · الكل) | Component داخل SCR-ROL-01 |
| SCR-SCP-02 | قسم "الصلاحيات الحساسة" (مفاتيح) | Section داخل SCR-ROL-01 |

### Use Cases
**UC-SCP-01 · تحديد النطاق لدور** — الممثل: Super Admin ← في صف الموديول يختار النطاق ← حفظ (ضمن UC-ROL-02) ← `ROLE.SCOPE_CHANGED`.

**UC-SCP-02 · منح/سحب صلاحية حساسة** — تفعيل مفتاح (مثلاً `data.wages.view`) ← تحذير «هتفتح بيانات سرية» + سبب + Step-up ← `ROLE.SENSITIVE_GRANTED`.

**UC-SCP-03 · تطبيق النطاق (سلوك النظام)** — أي استعلام يُفلتر على الخادم حسب (user, role, scope): `own` = `owner_id/sales_rep_id = user` · `team` = مرؤوسو `manager_id` · `department` · `all`. القيمة المحجوبة (تكلفة/أجر) **تُحذف من الاستجابة** مش بس تُخفى.

### User Stories + AC
- **US-SCP-01** كمدير نظام أريد أخلي مندوب المبيعات يشوف عملاءه فقط.
  - AC: الاستعلام يرجع عملاءه فقط · تجربة الوصول لعميل غيره = 403 مسجّل.
- **US-SCP-02** كمدير نظام أريد أمنع موظف المبيعات من التكاليف.
  - AC: لا يظهر عمود/حقل التكلفة في أي شاشة ولا في الـAPI.
- **US-SCP-03** كمدير نظام أريد أفصل إنشاء/اعتماد/تنفيذ سند الصرف.
  - AC: ثلاثة مفاتيح مستقلة · نفس الشخص لا يعتمد ما أنشأه.

### قواعد
- **BR-SCP-01** الأجور: HR ومن تمنحه الإدارة صراحةً؛ General Manager ليس تلقائيًا (**Pending بند 46**).
- **BR-SCP-02** نطاق `team` يتطلب `manager_id` صحيح؛ مستخدم بدون مدير = لا يظهر في أي فريق (تنبيه).
- **قرار مطلوب:** اعتماد النموذج كاملاً (README، قرار 2).

## SA-04 · أمان حسابات Super Admin — P0 · [Pending بند 35]

**Epic story:** كصاحب شركة أريد حساب أساسي وحساب احتياطي محميين بـMFA، عشان النظام عمره ما يتقفل عليّا ولا يتسرق.

### الشاشات
| ID | الاسم | النوع | Route |
|----|-------|-------|-------|
| SCR-SAC-01 | أمان Super Admin (الحسابين، MFA، آخر دخول) | Tab/Page | `/super-admin/users/security` |
| SCR-SAC-02 | تسمية الحساب الاحتياطي | Wizard | — |
| SCR-SAC-03 | إعداد MFA | Flow | — |
| SCR-SAC-04 | أكواد الاسترجاع [New] | Dialog | — |

### Use Cases
**UC-SAC-01 · تسمية الحساب الاحتياطي** — الممثل: Owner ← اختيار/إنشاء شخص تسميه الإدارة ← Step-up ← إعداد MFA له ← `SUPERADMIN.BACKUP_NAMED`. (مين الشخص **{Open}**).

**UC-SAC-02 · إعداد/تغيير MFA** — QR + كود تأكيد ← حفظ أكواد استرجاع ← `SUPERADMIN.MFA_CHANGED`. (الطريقة **{Open}**).

**UC-SAC-03 · استرجاع الأساسي بواسطة الاحتياطي** — الحساب الأساسي موقوف/فقد MFA ← الاحتياطي يدخل ← يفك القفل/يعيد MFA بإجراء موثّق ← `SUPERADMIN.RECOVERY_USED` (حرج).

**UC-SAC-04 · تعطيل حساب Super Admin** — مسموح فقط لو يتبقى حسابان نشطان على الأقل **[New]** ← Step-up ← Audit.

### AC
- **US-SAC-01** AC: لا يمكن ترك النظام بأقل من حسابَي Super Admin نشطين · الاحتياطي مربوط بـMFA قبل ما يتفعّل.
- **US-SAC-02** AC: أي استخدام لأكواد الاسترجاع يُسجَّل بخطورة حرجة ويُبلَّغ الحساب الآخر.

### مفتوح
مين الاحتياطي · طريقة MFA · قائمة الأحداث الحساسة · مدة الاحتفاظ بالسجل.

## SA-06 · حسابات التجار الخارجية — P0/P1 · [Pending بنود 32 و34]

**Epic story:** كصاحب شركة أريد أتابع طلبات فتح حساب التاجر وحسابات التجار، من غير ما أخلط بينهم وبين المستخدمين الداخليين.

### الشاشات
| ID | الاسم | Route |
|----|-------|-------|
| SCR-DLR-01 | طلبات التسجيل | `/super-admin/dealers/requests` |
| SCR-DLR-02 | تفاصيل الطلب (Drawer) | `/super-admin/dealers/requests/:id` |
| SCR-DLR-03 | حسابات التجار | `/super-admin/dealers` |
| SCR-DLR-04 | تفاصيل حساب التاجر | `/super-admin/dealers/:id` |

### Use Cases
**UC-DLR-01 · اعتماد طلب تسجيل** — الممثل: **المبيعات (الأصل)** أو Super Admin بصلاحية `sa.dealers.override` ← فتح الطلب (منشأة، مسؤول، مدينة، مستندات **{Open بند 32}**) ← اعتمد ← ينشئ حساب التاجر + يربط سجل عميل + يعيّن قائمة أسعار ← إشعار للتاجر ← `DEALER.REQUEST_APPROVED`.
**UC-DLR-02 · رفض أو طلب استكمال** — سبب إلزامي يصل للتاجر ← `REJECTED` / `NEEDS_INFO` (الأخيرة **[New]**).
**UC-DLR-03 · إيقاف/تفعيل حساب تاجر** — Confirm + سبب ← `DEALER.SUSPENDED`.
**UC-DLR-04 · تعيين/تغيير قائمة الأسعار** — يمر على اعتماد إن لزم (SA-12) ← `PRICELIST.CHANGED`. (مين يملك التعديل داخل المبيعات **{Open بند 31}**).
**UC-DLR-05 · تجاوز قرار المبيعات** — Super Admin يعكس قرارًا ← Step-up + سبب ← `DEALER.OVERRIDDEN` (حرج).

### AC
- **US-DLR-01** AC: لا حساب فعّال بدون اعتماد (لا تسجيل ذاتي) · التاجر لا يدخل قبل الاعتماد.
- **US-DLR-02** AC: حساب التاجر لا يظهر في قائمة المستخدمين ولا يشارك أدوار RBAC.
- **US-DLR-03** AC: التاجر لا يرى بيانات عملاء آخرين ولا التكاليف الداخلية (بند 27 Approved).

### تضارب لازم يتحسم
الشاشة الحالية تعرض "قبول/رفض" داخل Super Admin، وبند 32 ينص أن المبيعات تعتمد. **المقترح:** المبيعات تعتمد، والأدمن يرى ويتجاوز بسجل (قرار 1 في README).
